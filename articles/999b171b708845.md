## はじめに

v-tokyo Meetup #24で「[Astro Islandsの内部実装をざっくり解説](https://speakerdeck.com/knj/astro-islandsno-nei-bu-shi-zhuang-wo-ri-ben-de-fan-wakariyasuku-zatukurijie-shuo)」というタイトルで登壇しました。Vueコミュニティに向けて、Astroの中で何が起きているのかを話す機会をいただきました。

この記事では、ビルドからブラウザまで、`<astro-island>` というカスタム要素の中で何が動いているのかを掘り下げます。

Islands Architectureの全体像や使い方については、React Summit 2025で[Reuben Tier](https://github.com/TheOtterlord)さんが話しています。[Navigating Islands of Interactivity](https://gitnation.com/contents/navigating-islands-in-astro)というトークで、概念・歴史・状態管理まで広くカバーしています。併せて見ると理解が深まるはずです。

## クライアントとサーバーの境界をコンポーネント単位で決める

ウェブは昔からずっと似たような構造を繰り返しています。2層構造です。

![ウェブは昔からずっと似たような構造を繰り返している](/images/v-tokyo-00.png)

2000年代、PHPがサーバーでHTMLを生成して、動かしたいところだけjQuery Pluginを足す。2020年代、Astro Componentがビルド時にHTMLを生成して、動かしたいところだけIslandにする。そして今、Server Componentがサーバーで実行されて、必要なところだけClient Componentにする。

時代やフレームワークは違うのに、やっていることの構造は似ています。クライアントとサーバーの境界を、コンポーネント単位で決められます。これがウェブの普遍的なパターンです。

NuxtとAstroはどちらもこの構造を持っていますが、デフォルトが逆です。

![Nuxt 引き算としてのアプローチ、Astro 足し算としてのアプローチ](/images/v-tokyo-01.png)

NuxtはSPAが前提です。Universal RenderingではサーバーでHTMLを生成しますが、その後クライアント側でVueアプリケーション全体のハイドレーションが走ります。全コンポーネントツリーが再構築される。HTMLは返ってくるけど、その後の「ハイドレーション税」は全部払っています。そこから一部を外す、引き算のアプローチです。

AstroはMPAが前提です。ハイドレートしない状態がデフォルトで、そこから一部を足す。足し算のアプローチです。

## Astroのアーキテクチャ

Astroの基本は2層構造です。Astro Componentという静的HTMLの海と、そこに浮かぶIsland。

![Astro構成として Astro Component、Client Island、Server Island](/images/v-tokyo-02.png)

Islandには2種類あります。

- Client Island — クライアントでハイドレートされる（`client:visible` など）
- Server Island — サーバーでレンダリングを遅延する（`server:defer`）

ここで注目したいのは、どちらも「遅延」という思想を共有している点です。Server Islandは「動的」ではなく「遅延」です。静的なシェルを即座に返して、重い部分のレンダリングは後回しにする。Client Islandの `client:visible` も、見えるまでハイドレーションを後回しにする。

全部を一気にやらない。準備だけ先にして、必要な瞬間に実行する。この思想でAstro全体が設計されています。この「遅延」という考え方は、フレームワークのレイヤーに閉じた話ではありません。仕様レベルでも同じ思想が進んでいます。

TC39の [`import defer`](https://github.com/tc39/proposal-defer-import-eval)（Stage 3）は、JavaScriptのモジュール評価を遅延する言語レベルの仕組みです。モジュールはロード済みですが、プロパティへアクセスするまで実行しません。Astroの `server:defer` とはレイヤーが異なりますが、「必要になるまで実行を遅らせる」という思想は共通しています。[Oxc](https://github.com/oxc-project/oxc)はすでにパース対応済みで、[TypeScript 5.9](https://devblogs.microsoft.com/typescript/announcing-typescript-5-9/)も構文を認識しています。

ここからはClient Islandに焦点を当てます。ビルドからブラウザまで、中で何が起きているのかを見ていきます。

## ビルドタイム：コンパイラからブラウザへ

### コンパイラの分岐

Astroのコンパイラは `.astro` ファイルを読み込んだとき、`client:*` ディレクティブを探しています。

- `client:` がなければ、ただのHTMLにして終わり。JSは一切出力されない
- `client:` があれば、Islandとして抽出される

![](/images/v-tokyo-05.png)

### Propsシリアライズ

抽出されたIslandに対して、まずPropsのシリアライズが走ります。サーバーで渡されたデータを、ブラウザで復元できる文字列に変換する処理です。

ただのJSONではありません。`Date`や`Map`、`Set`もシリアライズできます。内部では[devalue](https://github.com/sveltejs/devalue)というライブラリが使われています。Svelteの作者、Rich Harrisが作ったものです。

### Viteによるコード分割

次にコード分割です。Viteが、そのコンポーネントに必要なJSだけを個別のチャンクとして切り出します。

`Counter`と`Search`があれば、それぞれ独立したJSファイルになります。でもVueのレンダラーは1つだけ。同じページにVueコンポーネントが何個あっても、ランタイムは共有されます。

### `<astro-island>` でラッピング

最後にラッピングです。サーバーサイドレンダリングされたHTMLを `<astro-island>` というカスタム要素で包みます。

```html
<astro-island
  component-url="/_astro/Counter.abc123.js"
  renderer-url="/_astro/client.vue.def456.js"
  props='{"count":[0,1]}'
  client="visible"
>
  <!-- SSR済みのHTML -->
  <div>Counter: 0</div>
</astro-island>
```

この属性を見てください。`component-url`がJSファイルのパス、`renderer-url`がレンダラーのパス、`props`がシリアライズされたデータ、`client`がどのディレクティブを使うか。ハイドレーションに必要な情報が全部この1つのHTMLタグに入っています。

## `<astro-island>`

`<astro-island>` はWeb Components、つまりブラウザ標準のカスタム要素です。

```typescript
class AstroIsland extends HTMLElement {
  connectedCallback() {
    this.childrenConnectedCallback();
  }

  async start() {
    const directive = this.getAttribute('client') as directiveAstroKeys;
    // Astro['load'], Astro['idle'], Astro['visible'], Astro['media'] を呼ぶだけ
    await Astro[directive]!(
      async () => {
        const [componentModule, { default: hydrator }] = await Promise.all([
          import(this.getAttribute('component-url')!),
          import(this.getAttribute('renderer-url')!),
        ]);
        this.Component = componentModule[this.getAttribute('component-export') || 'default'];
        this.hydrator = hydrator;
        return this.hydrate;
      },
      opts,
      this,
    );
  }
}

customElements.define('astro-island', AstroIsland);
```
*[実際のソースコード](https://github.com/withastro/astro/blob/ee3ab41a54601ec990d71d7f566f33939ecc6828/packages/astro/src/runtime/server/astro-island.ts#L49)から抜粋・簡略化*

`connectedCallback` → `start()` と呼ばれ、`Astro[directive]!()` で振り分けているだけです。`Astro['load']`、`Astro['visible']` といったグローバルオブジェクトのプロパティを呼ぶだけ。これがIslandハイドレーションの全体像です。

### Custom Elements APIだけを使う理由

![ちょうどいい仕組みだから Astroが使うのはCustom Elements APIだけ](/images/v-tokyo-03.png)

Astroが使うのはCustom Elements APIだけです。Shadow DOMやHTML Templatesは使っていません。Web Componentsのフルスペックではなく、一番薄い部分だけを借りています。

なぜCustom Elementsが「ちょうどいい」かというと、`connectedCallback`です。ブラウザがHTMLをパースして `<astro-island>` を見つけた瞬間、この関数が自動で発火します。Astro側で「どの要素がIslandか」を探し回る必要がありません。HTMLに書いた時点で、ブラウザがハイドレーションの起点を作ってくれます。

### Shadow DOMを使わない設計判断

`<astro-island>` は見た目を持たない透明な箱です。ページのCSSがそのまま中に届く必要があります。Shadow DOMで囲んでしまうと、その透明性が壊れます。

中身がVueやReactで、それぞれ自前のスタイル管理を持っています。TailwindのグローバルクラスがShadow DOMの壁で届かなくなると困ります。だから使いません。

HTML Templatesも同様です。「まだレンダリングされないDOMを保持する」ものですが、`<astro-island>` の中にはSSR済みのHTMLがもう入っています。テンプレートとして保持する必要がありません。

Astroが欲しかったのは `connectedCallback` というたった1つの機能だけです。

### mizchiさんのLunaにも注目

Web ComponentsのSSRという文脈では、Declarative Shadow DOMを使ってSSR + Hydrationを実現するアプローチもあります。mizchiさんの[Luna](https://zenn.dev/mizchi/articles/moonbit-luna-ui)がまさにそれをやっています。おそらく、Astroとは設計のゴールが異なりますが、Web標準をどう活用するかという点で非常に興味深いプロジェクトです。

## connectedCallbackの中身：ブラウザ標準APIだけ

![Astro Islandの内部 connectedCallbackからload/idle/visible/mediaへの分岐](/images/v-tokyo-04.png)

`start()` の中で `Astro[directive]!()` が呼ばれると、[各ディレクティブの実装](https://github.com/withastro/astro/tree/main/packages/astro/src/runtime/client)に処理が渡ります。それぞれの実装はブラウザ標準APIを使っているだけです。

条件を満たしたら `import(component-url)` でコンポーネント本体を取得し、`import(renderer-url)` でレンダラーを取得して、ハイドレートします。条件を満たすまで、この処理は一切走りません。ネットワークリクエストすら発生しません。

ここで一歩引いて見てください。全部ブラウザ標準APIです。Astro固有のコードは、この振り分けロジックだけです。独自のランタイムがほぼない。 だからAstroは速いのです。（Webが遅い説はありますが）

## さいごに

AstroのCEO、Fred K. SchottさんはGoogleのPolymerチームにいました。Web Componentsだけでアプリが作れることを証明しようとしたプロジェクトです。PolymerはReactやVueに押されましたが、FredはここでWeb標準APIの力を体で知りました。

だからAstroは、Islandの管理に独自のランタイムを作るのではなく、ブラウザが最初から持っているWeb Componentsを使っています。一貫して彼が言っているのは「HTMLこそがWebの主役であるべきだ」ということです。
