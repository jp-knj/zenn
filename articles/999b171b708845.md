## はじめに

Astro Islandsの内部実装を解説します。ビルドからブラウザまで、`<astro-island>` の中で何が動いているのかを見ていきます。

Islands Architectureの全体像や使い方については、React Summit 2025でReuben Tierさんが話しています。「Navigating Islands of Interactivity」というトークで、概念・歴史・状態管理まで広くカバーしています。併せて見ると理解が深まるはずです。

この記事では、その中の `<astro-island>` というカスタム要素を開いて、中の仕組みを掘り下げます。

## クライアントとサーバーの境界をコンポーネント単位で決める

ウェブは昔からずっと似たような構造を繰り返しています。

2000年代、PHPがサーバーでHTMLを生成して、動かしたいところだけjQuery Pluginを足す。2020年代、Astro Componentがビルド時にHTMLを生成して、動かしたいところだけIslandにする。そして今、Server Componentがサーバーで実行されて、必要なところだけClient Componentにする。

時代やフレームワークは違うのに、やっていることの構造は似ています。クライアントとサーバーの境界を、コンポーネント単位で決められる。これがウェブの普遍的なパターンです。

NuxtとAstroはどちらもこの構造を持っていますが、デフォルトが逆です。

NuxtはSPAが前提です。Universal RenderingではサーバーでHTMLを生成しますが、その後クライアント側でVueアプリケーション全体のハイドレーションが走ります。全コンポーネントツリーが再構築される。HTMLは返ってくるけど、その後の「ハイドレーション税」は全部払っています。そこから一部を外す、引き算のアプローチです。

AstroはMPAが前提です。ハイドレートしない状態がデフォルトで、そこから一部を足す。足し算のアプローチです。

## Astroのアーキテクチャ：2層構造

Astroの基本は2層構造です。Astro Componentという静的HTMLの海と、そこに浮かぶIsland。

Islandには2種類あります。

- Client Island — クライアントでハイドレートされる（`client:visible` など）
- Server Island — サーバーでレンダリングを遅延する（`server:defer`）

ここで注目したいのは、どちらも「遅延」という思想を共有している点です。Server Islandの `server:defer` は「動的」ではなく「遅延」です。静的なシェルを即座に返して、重い部分のレンダリングは後回しにする。Client Islandの `client:visible` も、見えるまでハイドレーションを後回しにする。

全部を一気にやらない。準備だけ先にして、必要な瞬間に実行する。この思想でAstro全体が設計されています。

:::message
TC39 `import defer` との関係

TC39で提案されている `import defer`（Stage 3）は、JavaScriptのモジュール評価を遅延する言語レベルの仕組みです。モジュールはロード済みですが、プロパティへアクセスするまで実行しません。Astroの `server:defer` とはレイヤーが異なりますが、「必要になるまで実行を遅らせる」という思想は共通しています。将来的にAstroが `import defer` を内部で活用する可能性もあります。Islandのコンポーネントコードを `import defer` でロードしておき、ハイドレーション条件を満たしたときに初めて評価する組み合わせは自然です。
:::

この記事では主にClient Islandの話をします。ビルドからブラウザまで、中で何が起きているのか。

## ビルドタイム：コンパイラからブラウザへ

### コンパイラの分岐

Astroのコンパイラは `.astro` ファイルを読み込んだとき、`client:*` ディレクティブを探しています。

- `client:` がなければ、ただのHTMLにして終わり。JSは一切出力されない
- `client:` があれば、Islandとして抽出される

### Propsシリアライズ

抽出されたIslandに対して、まずPropsのシリアライズが走ります。サーバーで渡されたデータを、ブラウザで復元できる文字列に変換する処理です。

ただのJSONではありません。`Date`や`Map`、`Set`もシリアライズできます。内部ではdevalueというライブラリが使われています。Svelteの作者、Rich Harrisが作ったものです。

### Viteによるコード分割

次にコード分割です。Viteが、そのコンポーネントに必要なJSだけを個別のチャンクとして切り出します。

`Counter`と`Search`があれば、それぞれ独立したJSファイルになります。でもVueのレンダラーは1つだけ。同じページにVueコンポーネントが何個あっても、ランタイムは共有されます。

### `<astro-island>` でラッピング

最後にラッピングです。サーバーサイドレンダリングされたHTMLを `<astro-island>` というカスタム要素で包みます。

```html
<astro-island
  component-url="/_astro/Counter.abc123.js"
  renderer-url="/_astro/client.vue.def456.js"
  props='{"count":[0,1]}'
  client="visible"
>
  <!-- SSR済みのHTML -->
  <div>Counter: 0</div>
</astro-island>
```

この属性を見てください。`component-url`がJSファイルのパス、`renderer-url`がレンダラーのパス、`props`がシリアライズされたデータ、`client`がどのディレクティブを使うか。ハイドレーションに必要な情報が全部この1つのHTMLタグに入っています。

## `<astro-island>` の正体：Web Components

`<astro-island>` はWeb Components、つまりブラウザ標準のカスタム要素です。

```typescript
class AstroIsland extends HTMLElement {
  connectedCallback() {
    // ハイドレーションがここから始まる
  }
}
customElements.define('astro-island', AstroIsland);
```

`class AstroIsland extends HTMLElement`。`connectedCallback` の中でハイドレーションが始まる。そして `customElements.define` でブラウザに登録する。これだけです。

### Custom Elements APIだけを使う理由

Astroが使うのはCustom Elements APIだけです。Shadow DOMやHTML Templatesは使っていません。Web Componentsのフルスペックではなく、一番薄い部分だけを借りています。

なぜCustom Elementsが「ちょうどいい」かというと、`connectedCallback`です。ブラウザがHTMLをパースして `<astro-island>` を見つけた瞬間、この関数が自動で発火します。Astro側で「どの要素がIslandか」を探し回る必要がありません。HTMLに書いた時点で、ブラウザがハイドレーションの起点を作ってくれます。

### Shadow DOMを使わない設計判断

`<astro-island>` は見た目を持たない透明な箱です。ページのCSSがそのまま中に届く必要があります。Shadow DOMで囲んでしまうと、その透明性が壊れます。

中身がVueやReactで、それぞれ自前のスタイル管理を持っています。TailwindのグローバルクラスがShadow DOMの壁で届かなくなると困ります。だから使いません。

HTML Templatesも同様です。「まだレンダリングされないDOMを保持する」ものですが、`<astro-island>` の中にはSSR済みのHTMLがもう入っています。テンプレートとして保持する必要がありません。

Astroが欲しかったのは `connectedCallback` というたった1つの機能だけです。

### mizchiさんのLunaにも注目

Web ComponentsのSSRという文脈では、Declarative Shadow DOMを使ってSSR + Hydrationを実現するアプローチもあります。mizchiさんのLunaがまさにそれをやっています。おそらく、Astroとは設計のゴールが異なりますが、Web標準をどう活用するかという点で非常に興味深いプロジェクトです。

## connectedCallbackの中身：ブラウザ標準APIだけ

`connectedCallback` の中では、まず `this.getAttribute('client')` でディレクティブを読みます。そしてディレクティブに応じて、異なるブラウザ標準APIで条件を設定します。

| ディレクティブ | ブラウザAPI | 動作 |
|---|---|---|
| `client:load` | 即時実行 | ページ読み込み時にすぐハイドレート |
| `client:idle` | `requestIdleCallback` | ブラウザが暇になったらハイドレート |
| `client:visible` | `IntersectionObserver` | ビューポートに入ったらハイドレート |
| `client:media` | `matchMedia` | メディアクエリにマッチしたらハイドレート |

条件を満たしたら `import(component-url)` でコンポーネント本体を取得し、`import(renderer-url)` でレンダラーを取得して、ハイドレートします。条件を満たすまで、この処理は一切走りません。ネットワークリクエストすら発生しません。

ここで一歩引いて見てください。全部ブラウザ標準APIです。Astro固有のコードは、この振り分けロジックだけです。独自のランタイムがほぼない。 だからAstroは速いのです。（Webが遅い説はありますが）

## なぜWeb標準にこだわるのか：Fred K. Schottの軌跡

AstroのCEO、Fred K. SchottさんはGoogleのPolymerチームにいました。Web Componentsだけでアプリが作れることを証明しようとしたプロジェクトです。PolymerはReactやVueに押されましたが、FredはここでWeb標準APIの力を体で知りました。

次にSnowpackというESMネイティブのビルドツールを作りました。当時はWebpackの時代。でもブラウザはすでに `import`/`export` をサポートしている。だったらバンドルしなくていい。開発時のHMRがはやくなりました。これは後にViteが同じアプローチで大成功する話です。

でもViteでビルドが速くなっても、送るJSの量は減りませんでした。問題はビルドツールじゃなくてアーキテクチャでした。だからAstroは「ビルドツール」ではなく「フレームワーク」として作られました。

Polymerで学んだWeb標準の力。Snowpackで学んだESMネイティブの速さ。そして「JSを減らすにはアーキテクチャから変えるしかない」という気づき。この3つが合流したのがAstroです。

一貫して彼が言っているのは「HTMLこそがWebの主役であるべきだ」ということです。

## まとめ

Astroは、Islandの管理に独自のランタイムを作るのではなく、ブラウザが最初から持っているWeb Componentsを使っています。Web Componentsだからこそ、中身がVueであれReactであれSvelteであれ、同じ仕組みで動きます。
